# Incident Report: n8n OAuth "Unauthorized" Authentication Failure (ARCHIVE)

**Date:** 2026-03-09  
**Service:** n8n Workflow Automation  
**Severity:** High (Blocked External Integrations)  
**Status:** Archive / Obsolete

---

## 1. Executive Summary
During the integration of Google Calendar with n8n, users encountered a persistent `{"status": "error", "message": "Unauthorized"}` response immediately following successful Google permission consent. This incident blocked the "Visit Scheduling" automation workflow. The issue was traced to a multi-layered session handling failure caused by environmental misconfiguration and secure cookie policies.

---

## 2. Root Cause Analysis (RCA)

### A. Domain Mismatch & Session Cookie Isolation
The primary cause was **Cross-Domain Session Loss**. 
*   **The Scenario:** n8n was being accessed via `http://localhost:5678`, but the Google OAuth callback was directed to the public tunnel `https://[SUBDOMAIN].ngrok-free.dev`.
*   **The Mechanism:** Modern browsers implement strict **Cookie Isolation**. When the login flow started on `localhost`, a state cookie was set. Upon returning from Google to `ngrok-free.dev`, the browser refused to send the `localhost` cookie to the new domain.
*   **The Result:** n8n detected an "orphan" callback without a matching local session, triggering a security rejection.

### B. Configuration File Corruption
Investigation revealed that the `.env` file contained invisible control characters and malformed line endings. This caused certain variables (specifically `N8N_GOOGLE_REDIRECT_URI`) to be misread by the Docker environment, leading to a mismatch between the registered OAuth URI and the runtime URI.

### C. Encryption Key Instability
The absence of a persistent `N8N_ENCRYPTION_KEY` meant that n8n generated a new internal key on every container restart. This periodically invalidated existing encrypted credentials and session states.

---

## 3. Implemented Fixes

### Phase 1: Environment Stabilization
1.  **Rebuilt Configuration**: Re-initialized a clean `.env` file from scratch to eliminate encoding corruption.
2.  **Persistence Layer**: Hardcoded a stable `N8N_ENCRYPTION_KEY` in both the `.env` and `docker-compose.yml` to ensure session stability across restarts.

### Phase 2: Secure Cookie Optimization
1.  **SameSite Policy**: Updated the n8n service config with `N8N_COOKIE_SAMESITE=lax`. This explicitly allows the session cookie to be preserved during the "top-level" redirect from Google's servers back to our ngrok domain.
2.  **Auth Layer Suspension**: Temporarily disabled `N8N_BASIC_AUTH` to ensure that the Google API callback was not blocked by a secondary authentication challenge during the handshake.

---

## 4. Resolution Verification
*   **Action:** Centralized access via the singular `https://[SUBDOMAIN].ngrok-free.dev` domain.
*   **Result:** The browser successfully associated the state cookie with the ngrok callback.
*   **Verification:** Google Calendar credentials now authorize successfully, and tokens are correctly persisted in the database.

---

## 5. Prevention & Best Practices
1.  **Uniform Origin Access**: Always access automation dashboards via the same URL defined in the Redirect URI whitelist.
2.  **Environment Integrity**: Use stable encryption keys for any production-grade deployment to prevent "Secret Rot" during updates.
3.  **Tunnel Awareness**: When using tools like ngrok, ensure the `WEBHOOK_URL` and `N8N_EDITOR_BASE_URL` match the public hostname to prevent redirect loops.

---

## 6. Operational Guidance: ngrok vs. Localhost
To maintain the stability of the OAuth integration and ensure reliable webhook reception, the following operational rules must be followed:

*   **Primary Access Point**: Always access the n8n dashboard via the **ngrok URL** (`https://[SUBDOMAIN].ngrok-free.dev`). 
*   **Localhost Usage**: Avoid using `localhost:5678` for workflow configuration. While it may load, it will cause **Session Mismatch** errors during OAuth handshakes and may misconfigure Telegram webhook registration.
*   **Domain Consistency**: By using the public tunnel domain, the platform simulates a production environment, ensuring that session cookies and redirect callbacks remain within the same security origin.
